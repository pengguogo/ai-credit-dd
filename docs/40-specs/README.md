# Spec 规范（轻量 SDD）

> 只给跨模块功能写 spec。小改动、bug 修复直接做。
> 格式以本文件为准。章节名、顺序、表格列不要随手增减；要改标准，先改这里，再改各 skill 与已有文档。
> 操作步骤在 `.agents/skills/`，不要在 skill 里另写一套模板。

## 何时需要 spec

| 需要 | 不需要 |
|------|--------|
| 新场景包、新增公共能力（eval、确认流、上下文管理） | 改文案、修 bug |
| 改动跨两个以上负责人的目录 | 单个工具内部调整 |
| 涉及契约或表结构变更 | 纯样式调整 |

## 步骤与 Skill

每步完成后找相关负责人确认，再进入下一步。

| 顺序 | Skill | 产出 |
|------|--------|------|
| 1 | `code-write-requirements` | `requirements.md` |
| 2 | `code-write-design` | `design.md` |
| 3 | `code-split-tasks` | `tasks.md` |
| 4 | `code-implement-task` | 代码；只勾选已满足完成标准的任务 |
| 5 | `code-write-test-cases` | `test-cases.md`（设计用例；必须在单测之前确认） |
| 6 | `code-review-code` | 审查结论（阻塞 / 建议） |
| 7 | `code-write-unit-tests` | `ocft-backend/tests/` 中可追溯到设计用例的 pytest |
| 8 | `code-update-spec` | 需求一旦变化就插入：同步设计、任务、设计用例，确认后再改代码 |

`write-spec` 只负责按 1→3 串起来，不单独规定格式。

## 门禁

1. 需求状态不是「已确认」，不得写设计、不得拆任务、不得开发。
2. 设计状态不是「已确认」，不得拆任务、不得开发。
3. 每条验收标准至少有一条任务、一条设计用例。
4. 写单测前，设计用例须已确认，并覆盖全部验收标准。
5. 审查有阻塞项时，不得勾选验证任务。单测尚未写时，缺测试记为缺口，不单独当成实现错误；有人声明单测已完成时，缺测试是阻塞。
6. 需求、验收、接口或数据有变化：先 `code-update-spec`，再改代码。禁止在代码里临场扩大范围。

## 共同约定

- 需求、设计、任务各不超过一页。设计用例用一张表。
- 写可验证的结果，不写「尽快」「友好」「尽量」。
- 不确定的事实（官方格式、数据字段）标「待确认」，不要编。
- 禁止写死题目答案或结论；运行时不读评测标签与 `expected`。
- 接口字段只改 `/contracts`，spec 里只放链接。
- 状态只用：`草稿`、`已确认`、`已实现`。确认前保持草稿。
- 语气和粒度对齐 `docs/40-specs/observability/`，不要照抄其中的业务内容。

## 目录

```text
docs/40-specs/
  <功能名-kebab-case>/
    requirements.md   # 做什么、验收标准
    design.md         # 怎么做：接口、数据、模块改动
    tasks.md          # 可勾选的实现任务
    test-cases.md     # 设计用例，从验收标准派生
```

新目录登记到 `docs/INDEX.md`，状态「草稿」；确认后改「生效」。

## requirements.md 模板

```markdown
# <功能名> 需求

状态：草稿 | 已确认 | 已实现    负责人：

## 变更
无。

## 背景
一两句话：为什么要做、对应哪条评分项或红线。

## 用户故事与验收标准
1. 作为 <角色>，我希望 <能力>，以便 <价值>。
   - WHEN <条件> THEN 系统 SHALL <可观察的结果>
   - IF <异常> THEN 系统 SHALL <如实失败的方式，含 errorCode 或等价信号>

## 不做什么
明确排除项，防止范围膨胀。
```

验收标准写差的例子：`系统应该友好提示并尽量给出建议`。
验收标准写对的例子：`WHEN 申请编号不存在 THEN 系统 SHALL 返回 errorCode=not_found，且不生成结论`。

## design.md 模板

```markdown
# <功能名> 设计

状态：草稿 | 已确认    对应需求：已确认

## 方案概述
## 涉及模块与负责人
## 接口 / 契约变更（链接 /contracts）
## 数据变更（表、字段、迁移方式）
## 红线影响（对照 30-standards/redlines.md 逐条说明）
## 取舍（选择了什么、放弃了什么、何时重访）
```

红线影响必须按 R1–R9 逐条写，无影响也要写「无影响」。

## tasks.md 模板

```markdown
# <功能名> 任务

状态：草稿 | 已确认

- [ ] 1. <任务>（<模块名>，关联需求 1）
  - 完成标准：<可单独验证的结果>
- [ ] 2. 设计用例：覆盖全部验收标准（场景与文档，关联需求 1…n）
  - 完成标准：test-cases.md 已确认，每条验收标准至少一条用例
- [ ] 3. …
- [ ] N. 验证：跑测试 / eval / 一键启动（关联需求 1…n）
  - 完成标准：<命令与通过条件>
```

负责人写模块名（对照 `AGENTS.md` 目录归属）。已完成的任务不删；取消的保留原文，勾掉后加 `（取消：原因）`。

## test-cases.md 模板

```markdown
# <功能名> 设计用例

状态：草稿 | 已确认

| 编号 | 追溯 | 类型 | 前置 | 操作 | 期望 | 验证 |
|------|------|------|------|------|------|------|
| TC-1 | 需求 1 | 正常 | <数据或身份> | <一步可执行的操作> | <可观察结果> | 单测 \| 接口 \| 手工 |
```

- 编号 `TC-<数字>`，只增不改号。
- 类型只允许：正常、边界、异常、红线。
- 验证只允许：单测、接口、手工。
- 每条验收标准至少一行。作废的行保留，期望改为 `作废：原因`。
- 不写测试代码，不写评测题答案。

## 需求变更

用 `code-update-spec`。在 `requirements.md` 的「变更」下追加，不改旧条目：

```markdown
- YYYY-MM-DD：<什么变了，为什么>。同步：design <章节>、tasks <编号>、TC-<编号>。
```

然后只改受影响的设计章节、任务和用例。确认后再改代码。

## 赛时用法

抽签后第 1 小时，按上表 1→3 写完并冻结范围，其余人按 tasks 认领。范围冻结后，新增需求只能进「不做什么」，或走 `code-update-spec` 作为下一轮。
