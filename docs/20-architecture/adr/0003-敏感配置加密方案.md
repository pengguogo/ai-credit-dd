# 0003 敏感配置加密方案

状态：已采纳    日期：2026-10-22    提出方：Agent 核心

## 背景

数据库连接串、模型 API Key 不能以明文出现在仓库、文档和日志中。要求：团队成员能方便共享，评委机器能"一键启动"，不依赖外部服务。

## 备选方案

| 方案 | 做法 | 优点 | 缺点 | 适合场景 |
|------|------|------|------|----------|
| **A. 密文配置 + 本机主密钥（已采纳）** | `.env` 写 `enc:...`，运行时用 Fernet 解密，主密钥放 `~/.ocft/master.key` 或环境变量 | 零外部依赖；密文可入库；团队共享一把主密钥即可；报错明确 | 主密钥要私下分发；主密钥泄露等于全部泄露 | 小团队、比赛、本地启动 |
| B. 只用环境变量 | 密钥只放系统环境变量，`.env` 里不放 | 最简单；符合 12-factor | 每台机器手动配置；换机器要重配；无法随仓库共享 | CI / 容器部署 |
| C. 操作系统凭据库 | `keyring` 库写入 Windows 凭据管理器 / macOS 钥匙串 | 由系统保护，无明文文件 | 跨平台差异大；无头环境（评委服务器）不可用；每人要各自录入 | 个人开发机 |
| D. 密码派生密钥（KDF） | 用团队口令 + scrypt / PBKDF2 派生主密钥，无需密钥文件 | 不用分发文件，口令可口头传达 | 口令强度决定安全；每次启动需要输入或环境变量 | 想避免密钥文件的团队 |
| E. 非对称加密（age / GPG / SOPS） | 用公钥加密提交，各人私钥解密 | 可按人授权、撤销；成熟工具 | 引入外部二进制和学习成本；比赛时间紧 | 长期维护的团队项目 |
| F. 云密钥管理（KMS / Vault / Secrets Manager） | 密钥在云端，运行时拉取 | 审计、轮换、权限最完整 | 需要联网和云账号；违背"本地一键启动" | 生产环境 |
| G. 加密文件 + 启动时提示输入口令 | 整个 `.env` 加密，启动时手输口令 | 无常驻明文 | 打断一键启动；不适合无人值守 | 个人使用 |

## 决策

采用 **A**，并在其上保留 B 作为兜底（主密钥可用环境变量 `OCFT_MASTER_KEY` 提供，适合容器 / CI）。

理由：比赛要求本地一键启动全栈，评委环境不可控，所以不能依赖云服务或系统凭据库；团队 6 人只需共享一把主密钥；密文和代码一起管理，换机器不丢配置。

## 后果

- 好处：零依赖、可测试（`tests/test_secret_box.py`）、错误显式（密钥缺失、不匹配、被篡改都会报错）。
- 代价：主密钥需要私下分发；密文文件不能让主密钥一起被提交。
- 评委环境：交付时若需要评委机器直接调用模型，要提供 Key 的密文和主密钥（或让评委自填 Key）；在 README 中写明。
- 重访条件：团队扩大或需要按人撤销权限时，评估 E（SOPS / age）；上云部署时改用 F。
