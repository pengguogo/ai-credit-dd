# 0006 单一关系库统一持久化（MySQL，本地 SQLite 兜底）

状态：已采纳    日期：2026-10-22    提出方：数据层

## 背景

系统要持久化两类数据：业务事实（信贷申请、交易、理赔、文档等）和 Agent 执行记录（会话、run、工具轨迹、证据、审计、确认）。规则要求"写操作与审计在同一事务、审计只追加"，并且提交包必须本地一键启动、依赖离线内置。团队已准备 MySQL 8.0（云 + 本地）。

## 决策

- 所有持久状态放在同一个关系库，只经 `DATABASE_URL` 指定，SQLAlchemy 访问。部署和演示用 MySQL；没配置 `DATABASE_URL` 时退回本地 SQLite，测试用临时 SQLite 文件。
- 连接串以 `enc:` 密文写在本机 `.env`（见 [0003](0003-敏感配置加密方案.md)）。
- 不引入 Redis、向量库或消息队列。会话记忆、工具结果摘要、实体槽位写在 run 的 `context_snapshot` 里；实时 SSE 事件也从同一个库读。
- 业务事实表只存原始字段，不存结论或评测标签（红线 R4，待办 1-6）。

## 后果

- 好处：证据、审计和业务写入可以放在一个事务里；本地启动只依赖一个库，SQLite 兜底时不需要装任何服务；`sql_query` 的表白名单只需维护一份。
- 代价：没有语义检索。文档类赛题只能用关键词和规则抽取，长文档检索能力有限。SQLite 和 MySQL 的方言有差异，要两边都测。
- 2026-10-22 更新：数据库层已统一为一套（待办 2-2），模型在 `app/models.py`、引擎在 `app/db.py`，`sql_query`、评测、`python -m db.seed` 都复用它；原 `db/` 的三张副本表不再使用。表结构变化走 `app/migrations.py` 的版本化迁移（待办 2-3），自写、不引入 Alembic，只做建表、加列等增量变更。
- 2026-10-24 更新：开发、演示与评测统一用 MySQL，连接配置在 `config.yaml` 的 database 段（`enc:` 密文，优先于 `DATABASE_URL`），不再使用本地 SQLite 兜底；SQLite 只保留给自动化测试的临时库（代码里的 SQLite 分支因此保留）。
- 重访条件：赛题需要对大量非结构化文本做语义检索，或数据量超过单库查询的时限，再评估专用检索组件，并另写 ADR。
