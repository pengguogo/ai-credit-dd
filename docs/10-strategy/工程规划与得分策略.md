## 1. 规则 → 可提前准备的能力映射

| 官方硬要求 / 评分点 | 底座阶段能否完成 | 准备成什么样才算「完成」 |
|---------------------|--------------|--------------------------|
| 一键启动全栈（前+后+库+模型） | ✅ 必须 | `start.ps1`（评测机为 Windows）一条命令起齐，新人 5 分钟内跑通 |
| 运行时模型 = `deepseek-v4.1-flash` | ✅ 必须 | `llm.py` 默认即该模型；有健康检查接口 |
| 代码实现 Agent（禁扣子等） | ✅ 必须 | LangGraph 调度 model/tools，终态与工具仍自研；工具调用可观测 |
| 公开 Skill / MCP 可接入 | ✅ 强烈建议 | 至少接入 1–2 个 MCP/Skill，README 写清接入方式 |
| 答案可追溯、留痕、禁 Mock 答案 | ✅ 必须 | 每次决策写 `audit_logs`；证据链可查 SQL/检索片段 |
| 客观分：评测集正确率 | ⚠️ 题未知，准备「评测框架」 | 有 `eval/`：公开样例可跑分；非公开题只换输入即可 |
| 客观分：上下文 / 编排 / 可观测性 | ✅ 必须 | 会话记忆 + 多工具编排 + Trace/日志面板 |
| 客观分：合规（敏感词等，强制） | ✅ 必须 | 输入输出双端过滤，违规可拦截并记日志 |
| 主观分：业务价值 / 演示 / 创新 / 交互 | ✅ 可预先搭建 | 对话 + 轨迹 + 证据 + 确认工作台；路演脚本模板；交互闭环 demo |
| 周日 12:00 前提交含非公开题结果 | ✅ 流程 | 批量跑题脚本 + 结果导出格式（JSON/CSV）预留 |

**不能提前做的：** 真实赛题业务逻辑、官方测试集答案、针对某道题的特化 Prompt。  
**可以提前做的：** 一切与「题面无关、与工程/合规/评测/协作相关」的底座。

### P0｜完赛资格与反红线（不做 = 可能直接出局）

**目标：抽签当天任何题，都能在 2 小时内挂上「真 Agent + 真库 + 真模型」。**

| 序号 | 任务 | 验收标准 | 建议负责人 |
|------|------|----------|------------|
| P0-1 | 锁定运行时模型为 `deepseek-v4.1-flash` | 去掉其它默认模型；`.env` 只配 DeepSeek；断网/失败有明确错误而非静默假答案 | 后端公共层（Cursor×1） |
| P0-2 | MySQL 接通（本地 + 阿里云可切换） | `DATABASE_URL` 一切换即用；seed 可写入 `ai_marathon`；禁止把假数据写死在 Prompt | 后端公共层 |
| P0-3 | 一键启动脚本 | Win/Mac 各一版：起 MySQL 检查 → 后端 → 前端 → 打印访问地址与 `/docs` | DevOps/公共层 |
| P0-4 | Agent 代码骨架（非扣子） | 最小闭环：`用户问题 → Planner/Router → Tool(s) → 证据 → 结论`；工具含至少 `sql_query` | Agent 核心（Cursor×1 + Codex×1） |
| P0-5 | 审计与证据链 | 表：`audit_logs`（输入、工具名、SQL/检索原文、模型输出、最终结论、时间戳、操作人确认位） | 后端 |
| P0-6 | 合规过滤（强制项） | 敏感词/政治等词库 + 输入输出拦截；违规返回结构化拒绝，不编造业务答案 | 合规模块（可 Codex） |
| P0-7 | 禁止 Mock 答案的工程约束 | 工具层禁止写死「标准答案」；评测模式与演示模式分离；CI/自检脚本扫描可疑硬编码 | 全员约定 + 公共层 |

## 7. 得分策略（按得分杠杆排序）

### 7.1 先活着，再完美（资格分）

1. **本地一键启动**比花哨功能更重要——评测/评委第一印象是「能不能跑」。  
2. **运行时模型锁死 flash**——用错模型可能直接违规。  
3. **纯代码 Agent**——扣子/低代码 = 取消资格；MCP/Skill 只做增强并写进 README。  
4. **零 Mock 答案**——工具返回必须来自 DB/检索/计算；LLM 不得「直接给最终业务结论」而不经工具。

### 7.2 客观分：正确率是基本盘

1. 把系统做成「**答题机**」：统一 `run(question) -> {answer, evidence[]}`。  
2. 公开题（含结果）用来**拟合策略**：SQL 是否准确、是否多跳推理、拒答策略是否正确。  
3. 非公开题：**禁止猜测标准答案**；只用同一套 pipeline 批量跑，保证证据齐全。  
4. 对「证据不足」的题，宁可结构化拒答并说明缺什么，也不要编造——贴合红线且利于合规分。

### 7.3 客观分：工程三项是拉开差距的关键

| 能力 | 评委/AI 可能怎么看 | 你们怎么做「看得见」 |
|------|--------------------|----------------------|
| 上下文管理 | 多轮是否一致、是否丢约束 | 会话摘要 + 槽位 + 可导出 context |
| Agent 编排 | 是否真有规划/工具路由 | 状态图/节点名出现在 Trace |
| 可观测性 | 出问题能否定位 | 请求 ID、工具 IO、耗时、前端轨迹面板 |

**一句话：让机器和人都能「看见 Agent 在想什么、查了什么、为何下结论」。**

### 7.4 客观分：合规是强制项，当作「开关」不是「装饰」

1. 输入扫描 + 输出扫描；命中即拦截。  
2. 拦截也要写 audit（证明系统有效）。  
3. 金融表述避免绝对化承诺；高风险操作走「待业务确认」状态位（规则要求留痕）。

### 7.5 主观分：进前十后怎么赢路演

1. **演示路径 ≤5 步**：提问 → 自动调工具 → 展示 SQL/证据 → 给出结论 → 指出业务价值。  
2. **业务价值要可量化**：拦截金额、审批耗时、准确率对比（用你们 eval 跑出来的数）。  
3. **技术创新说清楚**：代码级编排、MCP 接入、规则+LLM 分工、可观测，而不是「我们用了大模型」。  
4. **交互体验**：轨迹面板 > 复杂动画；错误态、加载态、拒答态都要好看且诚实。  
5. **差异化话术**：「同类用工作流拼装，我们是可评测、可审计的工程化 Agent。」

### 7.6 时间分配建议（赛时约 26h，有效约 18h）

编排、记忆、可观测、合规底座已完成，赛时只做适配，占比相应下调。

| 用途 | 建议占比 | 说明 |
|------|----------|------|
| 公开题正确率 + 证据链 | 45% | 客观分大头 |
| 编排/记忆/可观测/合规适配 | 15% | 架构已就绪，只针对赛题补强 |
| 非公开题批量与提交物 | 15% | 周日上午不可翻车 |
| 前端演示与路演 | 15% | 为前十冲刺 |
| 缓冲/合并冲突 | 10% | 没有缓冲必炸 |

### 7.7 常见丢分坑（提前写进团队公约）

| 坑 | 后果 | 预防 |
|----|------|------|
| Prompt 里写死测试答案 | 触红线 / 取消资格 | 代码扫描 + 双人复查 |
| 演示用 Mock、提交用另一套 | 评测翻车、信任崩盘 | 唯一 pipeline |
| 现场换技术栈/换模型 | 超时、违规 | 底座阶段冻结 |
| 六人同时改公共层 | 合不进 main | 目录所有制 |

### 7.8 高分公式（团队共识）


## 9. 附录：工程建设原则

1. **分层建设**：`ocft-backend` 按 `agent/`、`tools/`、`compliance/`、`eval/` 分模块，业务能力统一以场景包（`scenarios/*`）形式接入。  
2. **SQLite → MySQL**：保留 SQLite 仅作开发兜底；交付默认 MySQL（与比赛数据源一致概率更高）。  
3. **规则引擎包在 Agent 编排之内**：规则负责算结论和证据，Agent 负责理解、规划、调用工具，让评测能识别为 Agent 工程，而不是普通 CRUD。  
4. 《初版方案手册》（已归档至 `docs/90-archive/`）可保留作场景灵感，**以本文 +《[比赛规则要求](../00-rules/比赛规则要求.md)》为准**。

## 10. 抽签后增补（对照《九大赛题介绍 PPT》，2026-10-24）

PPT 共 22 页。04 的题面、数据和七项功能以官方题目说明、提交材料说明、[企业信贷尽调 Spec](../40-specs/enterprise-dd/requirements.md)、[多 Agent 编排 Spec](../40-specs/dd-multi-agent/requirements.md)和[模块分工表](模块分工表.md)为准；本节只保留会改变赛时优先级的规划说明。

### 10.1 本题验收形态

PPT 第 4 页、第 20 页把九题分成三类。04 属于**系统截图型**：至少 3 张系统真实界面截图（建议覆盖完整尽调报告、财务分析明细、风险提示与反欺诈；自然语言问询可作第 4 张）。

专属提交说明在截图之外还要求 8–10 分钟演示视频（当场跑出结果，含一次追问）。专属说明优先，视频照交。比赛规则中的前十名路演（周日 13:30–16:00）仍然保留。三类形式都要求现场可以实时重算，结果必须是系统当场跑出来的。

04 的题目交付是系统截图，加上专属说明要求的演示视频。会话记录 jsonl 属于 02 / 03 / 05 / 06。评委现场改规则、当场重算属于 01 / 09。

### 10.2 评审维度②里规划还没单列的两项

PPT 第 21 页（题目说明 6.1 写得更细）的工程架构是四项：记忆、工具调用、Skill、会议与资产管理。§7.3 仍是赛前的「上下文 / 编排 / 可观测」三项，P1-6 把 Skill 写成「接入一个外部 MCP」。抽签后按下面两条补：

| 能力 | 本题要做到 | 现状 |
|------|------------|------|
| Skill | 把重复任务封装成可复用工作流，写明触发条件和输入输出契约。本题对应「解析一类财报科目」「执行一条反欺诈规则」，规则放 `scenarios/dd04/*.yaml`，改配置即可用于非公开的另一批企业 | 配置文件已在方案里；文档和 README 要写清触发条件与契约，供评审查「Skill 管理」 |
| 会议与资产管理 | 任务、待办、尽调报告、证据材料要能建档、检索、改状态、归档，形成闭环 | 方案和分工表没有对应功能，也没有负责人。赛时至少做最小闭环：报告与证据可列表、可改状态、可归档，并在技术方案里对照这四步写实现。建议由黎锦涛挂在工作台上 |

记忆（跨轮记住已确认的风险评级和财报口径，可查看、可纠正、可清除）和工具调用（选型正确、失败可重试或降级、结果真的影响结论）底座已有，按 04 的企业和口径接上即可。

### 10.3 路演用的量化，以及 30 秒的口径

PPT 第 9 页给出的业务量化是：传统尽调上门收财报、人工写报告，耗时 **3–5 天**。路演和答辩用这个对比系统的全链路自动完成，用 eval 跑出来的一致率作第二个数。

单笔 **≤ 30 秒** 只作为内部耗时统计目标。这份 PPT 和题目说明都没有规定 30 秒；该数字来自已删除的赛题一览旧截图。不要在技术方案或答辩里把它说成官方时限。

材料种类、命名、编码、PDF 与视频规格、17 条自查，以通用提交材料说明和 04 提交材料说明为准，分工表已指到人。规划日程补三条执行口径：
