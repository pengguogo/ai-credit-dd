## 1. 评委首先会看到什么

项目具备真实的 Agent 工程形态：统一入口、主控加六角色、并行解读、确定性财务计算、工具注册、证据、审计、人工确认、记忆操作和可视化工作台。不能将其归为“读几个 CSV 后只调一次模型”的简单应用。

决定当前上限的不是功能数量，而是以下三点：

1. **结论发布仍有绕过取证与法规约束的路径。** 本次故障注入中，无工具、无证据的放款结论以及虚构法规均被发布为 `succeeded`。
2. **字段正确没有保证解释正确。** 当前真实模型报告再次出现重大异常折减归因错误；事实校验能核对部分数字与编号，但尚不能可靠判断指标含义、否定趋势和因果关系。
3. **最终交付尚未闭环。** 正式材料和输出绑定旧版本，视频和联系方式缺失，封包取件路径错误，正式“非公开结果”仍是演练数据；异机干净 Windows 验收尚无闭环证据。

建议先修发布门禁、解释与交付一致性，再考虑增加功能。后台测试通过与业务全文正确应始终分别陈述。

## 5. 分级问题、证据与验收

分级：**P0**＝可能触及强制项/红线、建议阻止最终放行；**P1**＝显著影响业务正确、审计可信或提交完整；**P2**＝能力边界与工程改进。P0不等于已被官方认定违规，尤其故障注入证明的是防线缺口。

### J01 · P0 · 无证据业务结论仍可成功发布

- 依据：通用证据红线；项目R3、R4；题目6.1可解释性。
- 证据：`app/agent/engine.py:171–195`只在特定关键词或已调用工具时强制证据；`scenarios.py:101`仅匹配“风险评级|建议额度|尽调结论”。本次HTTP探针返回“该企业没有对外担保，也没有逾期，可以放款。”，`succeeded`、`evidenceIds=[]`、工具轨迹0条。见[probe-result.json](AI评委证据-20261025/probe-result.json)。
- 影响：模型省略工具或更换措辞就可能把未经证实的业务判断发布为成功；普通问询同样受影响。
- 整改：发布业务断言必须由可追溯事实支撑；允许闲聊/澄清，但不能靠三个关键词识别全部业务结论。复用前轮证据时建立明确的引用与版本关联。
- 验收：无担保/无逾期/可放款/拒贷等同义表达，无证据均不能成功发布；合法追问复用证据可查到来源；澄清仍可正常返回。
- 归属：Agent核心。

### J02 · P0 · “不编造法规”主要靠Prompt，发布端未强制

- 依据：题目6.1输出合规、专属通用纪律6。
- 证据：`app/compliance/checker.py:144–151`为词库与有限组合规则；角色Prompt虽写了不引用法规，本次注入“根据《虚构企业信贷尽调法》第999条，该企业必须获得贷款。”仍得到`succeeded`。见同一探针文件。
- 影响：能够被发布的虚构法律可能成为业务结论依据；有提示词约束不能证明满足强制合规项。
- 整改：当前无可信法规源时，对法规引述做拒发或转人工；若允许引用，须绑定可核验条文证据与版本。
- 验收：不存在的法名、条号、文号、真法名配假条文均被拦截；普通业务分析不受误伤。此项是抗模型失误的门禁测试，不声称本次真实模型实际编造该法规。
- 归属：合规与Agent核心。

### J03 · P1 · 业务确认可由自报请求头身份完成

- 依据：通用“业务人员确认须留轨迹”；题目审计可信要求。
- 证据：`app/deps.py:32–57`允许无Bearer时使用任意`X-Actor-Id`，且跳过RBAC；`run_service.py:357–394`落库该身份。本次探针未登录，自报`unverified_business_officer`，对另一身份创建的run确认成功HTTP200。
- 影响：有审计记录，但记录不能证明是谁确认；数据写接口也复用同类权限分支。管理员API使用独立登录约束，不能扩大声称所有管理员接口均可绕过。
- 整改：评测旁路与人工确认/业务数据写入权限分离；确认绑定可信登录或明确受控的评测身份机制。
- 验收：无登录、自报他人、失效token加请求头均不能人工确认或越权写数据；合法角色确认仍有版本、幂等和审计。

### 9.1 业务价值：缺的是收益证据，而不是运行速度数字

本次申请平均17.71秒，是模拟数据上系统生成结果的耗时，不能直接叫“节省尽调工时”。题目背景中的人工3–5天包含收集、核实等环节，本系统没有替代全部环节；不能做“3天降到18秒”的对比，也不能据此计算节省比例。

可核验的收益测算应在同一任务范围进行：

```text
单笔人工净节省分钟
  = 原流程完成同范围任务的人工投入
  - 新流程的数据准备、操作、复核、纠错与重做人工投入

期间净收益
  = 单笔人工净节省分钟 / 60 × 实际业务量 × 岗位小时成本
  - 模型、部署与运维的期间增量成本
```

机器等待是否计入人工投入要提前明确；错误率、要点遗漏、可用报告比例应与工时一起报告。未测量的值写“假设/待测”，不能用市场规模、模型速度或测试通过率替代。最小试点路径应说清：哪个岗位、从哪些现有业务表取数、只辅助哪一步、谁复核、出了错谁处置、何种质量/工时门槛才扩大使用。

本项按完整一档标准判断，当前只能稳妥放第三档；这不否认材料已经主动说约束与边界，也不意味着场景是玩具。

### 9.2 演示完整度：补一段可计时、可解释的新需求演示

第一档需要的是现场变化后的完整响应，而非切换到另一笔预设样本。可以在临时、明确标记的演练数据中，现场修改一个业务事实（如新增一笔逾期担保），从提交变更开始计时，完成导入/核验、实时重算、证据定位、结论差异解释。也可以修改一项明确的模拟政策阈值并展示版本与输出差异。

必须先说明：这只是演练变更，不是官方非公开结果；不改答案、不覆盖本报告原始证据。当前单笔17.71秒均值不能保证“整个修改流程≤3分钟”。展示成功之外，还应展示对象不明时主动澄清、模型或工具失败时的下一步、业务确认与报告导出。已有脚本写到了部分分支，但没有证据就不能给满档。

### 9.3 技术创新：把本题设计与两端取舍讲透

可指名的设计应是“确定性财务决策与生成解释分离，并用同run证据约束发布”，不是“用了多Agent”。证据入口是`app/tools/dd_calc.py`、`app/agent/dd_graph.py`、`dd_verify.py`及版本化场景配置；只称本项目自行实现的组合与规则，不宣称算法首创。

- 为什么不用更简单：仅拼CSV让模型直接成文，难以保证公式、单位、评级、额度与来源稳定；当前确定性计算和证据链针对这一难点。但仍应拿简化基线测量，而不是只靠推断。
- 为什么不用更复杂：本题输入为结构化模拟数据，当前没有必要为展示而增加向量库、知识图谱、任意自主规划或PDF/OCR；它们会引入更多依赖、延迟与验证成本。若后续输入变成非结构化材料，再按实际需求评估。
- 如何证明增益：固定相同输入、模型和验收口径，对照无确定性计算、无发布校验或更少角色的方案，比较数值错误、无依据主张、要点覆盖、人工复核时间、延迟和token。不能靠关闭保护获得更高表面成功率。

现有技术权衡说明已写出多角色的token/延迟代价、框架边界及不支持的能力，但尚未完成上述对照；因此第二档比第一档更符合现有证据。

### 9.4 交互体验：第一档的五个勾不能只按按钮存在计算

| 第一档要求 | 当前证据判断 |
|---|---|
| 主动澄清 | 有request_clarification及对象不明的提示规则；既往真实用例有证据，但本轮20条均是对象明确输入，未重新全量验证澄清 |
| 结果带依据 | 本轮20/20有证据；J01证明仍有无需证据即可发布的其他路径，因此不能说全路径保证 |
| 出错说人话给下一步 | 有结构化错误、中文提示和排障手册；最终界面完整恢复流程仍须走查，错误码本身不等于用户知道下一步 |
| 跨轮记忆 | 有实体槽位、历史、纠正/清除；已确认口径的长期复用不足，见J06 |
| 长任务有进度 | 有SSE、角色泳道和工具轨迹；历史A5与当前页面入口有证据；刷新恢复、取消和总时限仍需加强 |

第一档还要求这些行为在同一条真实用户任务中连贯成立，且事实可信。建议用一个未参与开发的人依次完成“模糊提问→澄清→尽调→追问→错误恢复→查看依据→确认/导出”，记录是否需要开发者口头补救；不能仅用开发者熟悉的固定输入给出最高档。

### 9.5 本次复评意见

**业务价值第三档；演示完整度、技术创新、交互体验均按第二档准备，现场演示档位保留待验。** 不能因已有17秒结果、多角色架构或精美报告就升到第一档。最有价值的补强是：一份同范围工时与质量测算，一段三分钟内响应临时变化的真实演示，一组更简单/更复杂方案的取舍证据，以及一条包含澄清和异常恢复的完整用户路径。
