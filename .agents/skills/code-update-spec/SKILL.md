# 更新需求

标准只以 `docs/40-specs/README.md` 的「需求变更」和模板为准。先读该功能目录里已有的四份文件（缺的就按对应 skill 补，不发明章节）。

顺序固定：需求 → 设计 → 任务 → 设计用例 → 契约或迁移说明 → 停下来确认 → 才允许改代码。

## 步骤

1. 用一两句写清这次变了什么、为什么。能对上某条验收标准或「不做什么」的，指出编号。
2. 改 `requirements.md`：
   - 在「变更」下追加一条，带日期，并点名要同步的设计章节、任务编号、用例编号。没有「变更」一节就按模板补上，不要改写更早的条目。
   - 改用户故事、验收标准或排除项。已实现的行为若被替换，旧标准删掉前先确认没有别的文档仍引用它；引用改到新编号。
   - 状态：确认前保持或改回「草稿」。不要留着「已确认」却改了验收标准。
3. 同步 `design.md` 里受影响的章节。方案若改了，取舍里补一句放弃了什么。红线 R1–R9 重新看一遍，有变化的改写，没变化的保留。
4. 同步 `tasks.md`：
   - 已勾选且仍然有效的不改写、不删除。
   - 不再做的：保留原文，改为勾选，末尾加 `（取消：原因）`。
   - 新工作追加任务，关联新的需求编号，写完成标准。验证任务的命令若变了，改完成标准，不要把已通过的验证假装仍然有效。
5. 同步 `test-cases.md`：新验收标准补行，编号继续递增。不再适用的行保留，期望改为 `作废：原因`。核对每条仍有效的验收标准至少有一条未作废用例。
6. 接口有变就先改 `/contracts`。表结构有变就在设计里写明新迁移，迁移代码等确认后再写。
7. `docs/INDEX.md` 该行若从「生效」回到待确认，状态改「草稿」。
8. 停下来，列出改了哪些文件、哪些任务和用例，请用户确认。确认前不要改业务代码。确认后把需求、设计、任务、设计用例中仍准确的状态改回「已确认」，再用 `code-implement-task` 做新增任务。

## 自查

- 四份文档和契约没有互相矛盾的验收结果。
- 没有人在代码注释或 Prompt 里用另一套标准顶替 spec。
- 变更条目可以独立读懂，不依赖对话记录。
