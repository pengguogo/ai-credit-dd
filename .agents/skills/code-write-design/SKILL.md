# 写设计

标准只以 `docs/40-specs/README.md` 为准。先读它和同目录已确认的 `requirements.md`。章节与 `design.md` 模板一致，不要另起一套。

## 门禁

`requirements.md` 状态不是「已确认」时停下来，先请用户确认需求。不要用设计补写未确认的需求。

## 步骤

1. 写 `docs/40-specs/<功能名>/design.md`，状态「草稿」，并写明对应需求已确认。
2. 方案概述只写选定的做法，能让负责人照着改代码。
3. 涉及模块与负责人对照 `AGENTS.md` 目录归属。跨公共层（`app/agent/`、`app/llm.py`、合规、可观测）时点名。
4. 契约：先改 `/contracts`，设计里只放链接，不复制字段表。没有契约变更就写「无」。
5. 数据：写明表、字段、写入哪一条 `app/migrations.py` 迁移（只增不删）。没有数据变更就写「无」。禁止只改 `app/models.py`。
6. 红线影响对照 `docs/30-standards/redlines.md` 的 R1–R9 逐条写。无影响写「无影响」。
7. 取舍写选择、放弃的做法、何时重访。
8. 停下来，请用户确认。确认前不要拆任务、不要开发。用户确认后把状态改为「已确认」。

## 自查

- 全文不超过一页。
- 每条验收标准都能在方案里找到落点；对不上就回到需求，用 `code-update-spec`，不要在设计里偷偷改验收。
- 没有写死题目答案，没有把评测 `expected` 写进运行时可读的数据。
