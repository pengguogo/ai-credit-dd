# 写需求

标准只以 `docs/40-specs/README.md` 为准。先读它。章节名和顺序与其中 `requirements.md` 模板一致，不要另起一套。

## 何时做

对照 README「何时需要 spec」。不需要 spec 时直接说明，不要建目录。

目录 `docs/40-specs/<功能名>/` 已存在且不是从零起草时，改用 `code-update-spec`。

## 步骤

1. 确认功能名（kebab-case）和负责人模块（对照 `AGENTS.md` 目录归属）。
2. 建 `docs/40-specs/<功能名>/requirements.md`，按模板填：状态写「草稿」。
3. 背景只写为什么做、对应哪条评分项或红线。
4. 每条用户故事下用 `WHEN … THEN 系统 SHALL …` 或 `IF … THEN 系统 SHALL …`。结果必须可观察（状态码、`errorCode`、字段、证据行、界面状态）。
5. 「不做什么」至少一条。
6. 「变更」初稿写「无。」
7. 在 `docs/INDEX.md` 登记，状态「草稿」。
8. 停下来，请用户确认。确认前不要写设计、不要拆任务、不要改代码。用户确认后把状态改为「已确认」。

## 自查

- 全文不超过一页。
- 没有「尽快 / 友好 / 尽量」这类无法验证的句子。
- 没有某题的答案、结论或题号到答案的映射。
- 不确定的官方格式或字段标了「待确认」。
