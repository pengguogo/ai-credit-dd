# 写设计用例

标准只以 `docs/40-specs/README.md` 为准。先读它、同目录 `requirements.md` 和 `design.md`。表格列与 `test-cases.md` 模板一致：编号、追溯、类型、前置、操作、期望、验证。

设计用例是给人和单测对照的验收表，不是 pytest 代码。写代码用 `code-write-unit-tests`。

## 门禁

需求不是「已确认」时停下来。设计还是草稿时可以起草用例，但不得把用例状态写成「已确认」。

## 步骤

1. 写或更新 `docs/40-specs/<功能名>/test-cases.md`，状态「草稿」。
2. 把每条 `WHEN/THEN`、`IF/THEN` 拆成至少一行。编号从 `TC-1` 递增，已有编号不改、不复用。
3. 类型只写：正常、边界、异常、红线。一条验收标准可以多行（例如正常一次、边界一次）。
4. 期望只写可观察结果：HTTP 状态、`errorCode`、响应字段、证据是否落库、界面四种状态（加载、失败、拦截、证据不足）之一。
5. 验证只写：单测、接口、手工。
   - 纯函数、工具 handler、合规规则、服务分支：单测。
   - 走 `TestClient` 的 HTTP 行为：接口。
   - 只能眼看的布局或演示路径：手工。
6. 红线类至少覆盖：结论有证据、失败不是模板化成功、输出不含评测标签。没有这类风险就不要硬编。
7. 核对清单：每条验收标准都有追溯；「不做什么」里容易被做成的项，用一条异常或红线用例挡住。
8. 在 `docs/INDEX.md` 该功能说明中带上设计用例。停下来请用户确认。确认后状态改为「已确认」，并把 tasks 里设计用例那条在完成标准满足时勾上。

## 禁止

- 写测试代码、夹具或具体断言实现。
- 写入评测集答案、`expected`、`is_fraud`、`extracted_kpis`。
- 删除或改号。不作数的行保留，期望改为 `作废：原因`。
