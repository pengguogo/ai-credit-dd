# 代码审查

先读 `docs/30-standards/review-checklist.md`，有对应 spec 时再读该目录的需求、设计、任务、设计用例。红线细则在 `docs/30-standards/redlines.md`。

审查只出结论。用户明确要求修时再改代码；阻塞项修完后重新审一遍。

## 范围

用户指定了任务编号或文件：只审那些改动。
没指定：审当前未提交 diff；若在功能分支上，再加上相对 `main` 的提交。回复第一句写明审查范围。

## 步骤

1. 逐项核对评审清单。不适用的写 N/A，不要跳过红线六项。
2. 有 spec 时额外核对：
   - 改动是否只覆盖已勾选或正在做的任务，有没有范围外行为。
   - 每条相关验收标准是否有证据（测试、接口响应或设计用例里的手工项）。
   - 设计用例里验证方式为「单测」「接口」的，是否有对应测试。单测按流程还没写：记入已核对的缺口，不列为阻塞。任务里单测已勾选，或用户声明单测已完成：缺测试是阻塞。
   - 契约、迁移是否与 design 一致。
3. 没有 spec 的小改动：只走评审清单，并写明「无 spec」。
4. 用下面的结构写结论，每条阻塞或建议都带文件位置，以及需求编号、用例编号或红线编号。

```markdown
# 审查：<功能或分支>

范围：<diff 范围>
结论：通过 | 需修改

## 阻塞
- [<编号>] `路径`: <问题>。期望：<可观察结果>

## 建议
- [<编号>] `路径`: <问题>

## 已核对
- 评审清单红线：通过或列出未过项
- 验收标准：需求 n 已覆盖 / 未覆盖
- 设计用例：TC-n 有测试 / 手工 / 缺失
```

没有阻塞项，结论才是「通过」。有阻塞项时，不要把 `tasks.md` 的验证任务勾上。

## 阻塞与建议

阻塞：红线、验收对不上、失败被写成成功、缺证据、分层被绕过、契约或迁移与设计不一致。
建议：命名、重复、缺少 `@why`、测试可以更紧，但不改变行为对错。
