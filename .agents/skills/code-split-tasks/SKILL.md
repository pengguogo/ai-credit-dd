# 拆任务

标准只以 `docs/40-specs/README.md` 为准。先读它、同目录 `requirements.md` 和已确认的 `design.md`。格式与 `tasks.md` 模板一致。

## 门禁

需求或设计的状态不是「已确认」时停下来，不要拆任务。

## 步骤

1. 写 `docs/40-specs/<功能名>/tasks.md`，状态「草稿」。
2. 一条任务只做一件可以单独验证的事，按依赖从先到后排。
3. 每条写成：
   - `- [ ] <序号>. <任务>（<模块名>，关联需求 <编号>）`
   - 下一行 `完成标准：` 写可观察结果，不写「完成开发」。
4. 模块名对照 `AGENTS.md` 目录归属。需要到人时再对照 `docs/10-strategy/模块分工表.md`。
5. 必须有一条「设计用例」任务，关联全部需求编号，完成标准指向 `test-cases.md` 已确认且覆盖全部验收标准。执行时用 `code-write-test-cases`。
6. 必须有一条单测任务，完成标准是设计用例里验证方式为「单测」或「接口」的编号都有对应 pytest。执行时用 `code-write-unit-tests`。
7. 最后一条必须是验证：写明命令（pytest、前端 lint/build、eval、一键启动里实际相关的那些）和通过条件。
8. 核对：每条验收标准至少出现在一条任务的「关联需求」里。漏了就补任务，不要并进一句「以及其他」。
9. 停下来，请用户确认分工。确认后把状态改为「已确认」。

## 自查

- 全文不超过一页。
- 不把「待确认」的事实拆成已经可做的实现任务。
- 新工具不在这里重写工具规范，任务里写「按 add-tool」。新场景写「按 add-scenario」。
